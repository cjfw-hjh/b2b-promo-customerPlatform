# PRD: 정성을 보여줘

## 1. 개요

**제품명**: 정성을 보여줘

**한 줄 설명**: B2B 영업사원이 정성적 영업활동(고객 관계 형성 활동)을 영업일지로 기록하고, 팀장이 코멘트로 코칭하며, 거래처별로 축적된 영업 노하우를 조직 전체가 공유하는 웹 서비스.

**배경**: 본 시스템은 매출, 가격, 할인율, 계약금액 등 정량적 영업성과를 관리하는 시스템이 아니다(도메인 정의서 1번, 19번). 영업사원이 실제 영업 과정에서 수행하는 정성적 활동과 고객 관계 형성 활동은 지금까지 개인의 기억이나 개별 보고에 머물러 조직 자산으로 남지 않았다. 본 시스템은 이 정성적 활동 기록을 팀장의 코멘트(코칭)와 거래처 단위의 Know-how 축적으로 연결하는 것을 목적으로 한다(PRINCIPLE-002).

## 2. 목표

도메인 정의서 20번 섹션(핵심 도메인 원칙)에서 도출한 정성적 목표만 다룬다. 수치화된 비즈니스 목표(매출, 팀 수 등)는 근거 문서에 존재하지 않으므로 설정하지 않는다.

- **정성적 활동 기록의 습관화** — 영업 결과가 아니라 관계 형성 과정에서 어떤 행동을 했는지를 기록하는 습관을 만든다 (PRINCIPLE-001).
- **개인 기록의 조직 자산화** — 개인의 영업일지를 일회성 보고로 끝내지 않고 거래처 단위 Know-how로 축적한다 (PRINCIPLE-002).
- **팀장 코칭의 체계화** — 팀장 피드백이 단순 확인이 아니라 코멘트 스레드를 통한 지속적 코칭으로 이어지게 한다 (PRINCIPLE-003).
- **단순한 작성 경험** — 매일 쓰는 도구이므로 작성 과정(거래처/영업형태/활동내역 3가지)을 최대한 단순하게 유지한다 (PRINCIPLE-004).
- **공유와 코칭의 분리** — 조직에 공유되는 Know-how와 개인 코칭 영역(팀장 피드백)을 명확히 분리한다 (PRINCIPLE-005).

## 3. 사용자 및 역할

회원가입 시 사용자는 역할을 반드시 선택하며(RULE-USER-001, RULE-USER-002), 역할은 영업사원 또는 팀장 두 가지뿐이다.

| 역할         | 권한 요약                                                                                                                                                              |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **영업사원** | 영업일지 작성/수정/삭제(RULE-LOG-002, 003), 본인 영업일지 조회·검색(RULE-SEARCH-001), 팀장 코멘트 확인 및 답변(RULE-REPLY-002), 거래처 Know-how 조회(RULE-KNOWHOW-006) |
| **팀장**     | 자신에게 매핑된 영업사원의 영업일지 조회(RULE-ORG-008), 코멘트 작성(RULE-FEEDBACK-003), 거래처 Know-how 조회(RULE-KNOWHOW-006)                                         |

팀장은 2차 상사에게 보고 체계를 확장하지 않으므로 별도의 상사 이메일을 입력하지 않는다(RULE-ORG-006).

## 4. 범위

### 4.1 MVP 포함 범위

도메인 정의서 2번(핵심 업무 흐름), 17번(영업사원 View), 18번(팀장 View)에 정의된 전체 흐름.

- 회원가입/로그인, 조직(상사 관계) 매핑
- 거래처 마스터 선택 기반 영업일지 작성/수정/삭제
- 활동 내역 텍스트 입력 및 STT 음성 입력
- 팀장 코멘트 ↔ 영업사원 답변의 코멘트 스레드
- 영업일지 등록/코멘트 등록 시 이메일 알림
- 본인 영업일지 조회/검색
- 거래처별 영업 Know-how 조회(조직 범위 제한)

### 4.2 명시적 제외 범위

**도메인 정의서 19번(시스템 범위 제외) 그대로 적용**: 상품, 단가, 할인율, 견적, 주문, 계약금액, 매출, 원가, 손익, 영업목표, 영업실적 평가, 인센티브, 성과급. 본 시스템은 CRM, ERP, 영업실적 관리 시스템을 대체하지 않는다.

**추가로, 21.2 남은 결정 사항 2건(도메인 정의서 원문 번호 5번, 7번)은 이번 MVP 범위에서 명시적으로 제외한다.**

- **[21.2 항목 5] 정성적 활동 검증 방식** (섹션 9, RULE-VALIDATION-001, RULE-VALIDATION-002, RULE-VALIDATION-003) — 구체적 검증 방식(키워드 탐지/AI 문맥 분류 등)이 미확정 상태이므로, MVP에서는 정량적 실적 표현을 자동으로 차단·검증하는 로직을 구현하지 않는다. 작성 가이드 문구 정도로만 안내한다.
- **[21.2 항목 7] 영업활동 내 고객 개인정보 공유 통제** — 활동 내역에 개인정보가 포함되어도 이를 별도로 통제하지 않는다. 실사용 전 재검토가 필요한 항목으로 남긴다.

기타 범위 외 사항: 거래처 마스터 관리자 화면(RULE-CUSTOMER-003), Google Calendar/Slack 등 외부 서비스 연동(추후 예정), 네이티브 모바일 앱, 접근성(a11y) 대응.

## 5. 기능 요구사항

### 5.1 인증 및 회원가입 (UC-001, UC-002)

- 입력 항목: 사번, 이메일, 비밀번호, 역할, (영업사원인 경우) 팀장 이메일.
- 사번은 6자리 (RULE-AUTH-001), 이메일은 정상 형식 (RULE-AUTH-002), 비밀번호는 7자리 이상 (RULE-AUTH-003).
- 사번 중복 불가 (RULE-AUTH-004), 이메일 중복 불가 (RULE-AUTH-005).
- 역할은 영업사원/팀장 중 하나를 반드시 선택 (RULE-AUTH-006, RULE-USER-002).
- 로그인 성공 시 역할에 따라 영업사원 View 또는 팀장 View로 라우팅 (UC-002).

### 5.2 조직 및 상사 관계 (UC-013)

- 영업사원은 회원가입 시 팀장 이메일을 필수 입력 (RULE-ORG-001), 정상 이메일 형식이어야 함 (RULE-ORG-002).
- 해당 이메일의 팀장이 아직 미가입이어도 회원가입 가능 (RULE-ORG-003), 이 상태에서도 영업일지 등록 알림 발송 가능 (RULE-ORG-004).
- 추후 동일 이메일로 팀장이 가입하면 기존 영업사원과 자동 연결 (RULE-ORG-005, UC-013).
- 팀장은 상사 이메일을 입력하지 않음 (RULE-ORG-006).
- 영업사원은 정확히 하나의 팀장에게만 매핑 (RULE-ORG-007), 팀장은 매핑된 영업사원만 조회·관리 (RULE-ORG-008). 별도의 조직/팀 엔티티는 두지 않고, "동일 팀장에게 매핑된 영업사원 집합"을 조직 단위로 취급한다 (5.3 조직 단위 정의).

### 5.3 거래처 마스터

- 영업일지 작성 시 사전 등록된 거래처 중 하나를 선택 (RULE-CUSTOMER-001).
- 영업일지 화면에서 신규 거래처 생성 불가 (RULE-CUSTOMER-002).
- 거래처 마스터는 별도 관리자 화면 없이 DB에 직접 등록·관리 (RULE-CUSTOMER-003). MVP에서는 등록/수정 UI를 제공하지 않는다.

### 5.4 영업일지 CRUD (UC-003, UC-005, UC-006)

- 필수 입력: 거래처, 영업 형태(외근/내근/기타), 활동 내역.
- 작성일은 시스템이 최초 등록 시점으로 자동 기록, 사용자가 임의 변경 불가 (RULE-LOG-001).
- 작성자 본인만 수정 가능 (RULE-LOG-002), 작성자 본인만 삭제 가능 (RULE-LOG-003).
- 수정해도 최초 작성일은 변경되지 않음 (RULE-LOG-004).
- 팀장 코멘트가 하나라도 등록된 영업일지는 작성자도 삭제 불가 — 단 수정은 코멘트 존재 여부와 무관하게 계속 가능 (RULE-LOG-005, UC-006).
- 활동 내역은 "무엇을 얼마에 팔았는가"가 아니라 "고객 관계를 위해 무엇을 했는가"를 기록하는 것이 원칙이다 (PRINCIPLE-ACTIVITY-001). 자동 검증 로직은 4.2에 따라 MVP 제외.

### 5.5 활동 내역 음성 입력 (STT) (UC-004)

- 브라우저 기본 Web Speech API(SpeechRecognition/webkitSpeechRecognition) 사용, 외부/유료 STT 서비스 사용 안 함 (RULE-STT-001).
- 기본 인식 언어는 한국어(ko-KR) (RULE-STT-002).
- 변환된 텍스트는 즉시 저장되지 않고 활동 내역 입력란에 반영되며, 사용자가 확인 후 저장 (RULE-STT-003).
- 저장 전 변환 텍스트를 자유롭게 수정/삭제 가능 (RULE-STT-004).
- 음성 입력과 직접 입력은 배타적이지 않고 혼용 가능 (RULE-STT-005).
- 음성 원본은 저장하지 않고 최종 반영된 텍스트만 영업일지 데이터로 저장 (RULE-STT-006).
- 브라우저 호환성/인식 정확도는 MVP에서 보장하지 않으며, 미지원 시 기존 방식(직접 입력)으로 대체 (RULE-STT-007).

### 5.6 팀장 영업일지 조회 (UC-007)

- 팀장은 자신에게 매핑된 영업사원의 영업일지 목록을 조회하고, 목록에서 하나를 선택해 상세 내용을 확인할 수 있다 (UC-007).
- 팀장은 자신에게 매핑되지 않은 영업사원의 개인 영업일지는 조회할 수 없다 (RULE-ORG-008, UC-007).
- 팀장 View에서는 코멘트(피드백)를 아직 작성하지 않은 영업일지를 별도로 확인할 수 있어야 하며, 자신이 과거에 작성한 코멘트 이력도 조회할 수 있다 (섹션 18).

### 5.7 코멘트 스레드 (피드백/답변) (UC-008, UC-009)

- 하나의 영업일지에 여러 개의 팀장 코멘트 등록 가능, 횟수 제한 없음 (RULE-FEEDBACK-001).
- 최초 코멘트는 반드시 팀장으로부터 시작 (RULE-FEEDBACK-002, RULE-REPLY-001).
- 코멘트 작성 권한은 해당 영업사원의 팀장에게만 있음 (RULE-FEEDBACK-003).
- 팀장 코멘트 등록 시마다 영업일지 작성자에게 이메일 알림 (RULE-FEEDBACK-004).
- 영업사원은 팀장 코멘트가 최소 1건 이상 있어야 답변 가능 (RULE-REPLY-001).
- 답변 작성 권한은 해당 영업일지 작성자 본인 (RULE-REPLY-002), 답변은 해당 영업일지·코멘트 스레드와 연결 (RULE-REPLY-003).
- 답변 등록 횟수 제한 없음 (RULE-REPLY-004), 등록 시마다 담당 팀장에게 이메일 알림 (RULE-REPLY-005).

### 5.8 이메일 알림 (UC-003, UC-012)

- 영업일지 저장 시 작성자의 팀장 이메일로 등록 알림 발송 (섹션 12.1).
- 코멘트/답변 등록 시마다 상대방에게 알림: 팀장 코멘트 → 작성자, 영업사원 답변 → 담당 팀장 (섹션 12.2).
- 피드백 미작성 건에 대한 별도 리마인드 알림은 제공하지 않음 (섹션 12.3).
- 팀장이 미가입 상태여도 등록된 팀장 이메일로 발송 시도 (UC-012).
- 이메일 발송 실패가 영업일지 또는 코멘트 저장을 취소시키지 않음 (RULE-NOTIFICATION-001).

### 5.9 개인 조회/검색 (UC-010)

- 본인이 작성한 영업일지만 조회/검색 (RULE-SEARCH-001).
- 검색 조건: 기간, 거래처, 영업 형태, 키워드.

### 5.10 거래처 Know-how 공유 (UC-011)

- 거래처 단위로 축적된 영업활동을 다른 영업사원도 조회 가능 (RULE-KNOWHOW-001), 공유 대상은 정성적 활동 내용 (RULE-KNOWHOW-002).
- 팀장 피드백 및 영업사원 답변은 공유 대상에서 기본 제외 — 개인 코칭 내용이므로 (RULE-KNOWHOW-003).
- 공유 화면에는 작성자·작성일 표시 가능 (RULE-KNOWHOW-004).
- 삭제된 영업일지는 공유 대상에서 제외 (RULE-KNOWHOW-005).
- 조회 범위는 조회자와 동일한 팀장에게 매핑된 영업사원 그룹으로 제한 (RULE-KNOWHOW-006).

### 5.11 영업일지 상태

- 상태는 "작성 완료" → "코멘트 진행중" 두 가지뿐이며, 팀장 또는 영업사원이 코멘트를 1건이라도 남기면 "코멘트 진행중"으로 전환된다 (섹션 16).
- 별도의 종료 상태나 임시저장 상태는 정의하지 않는다.

## 6. 비기능 요구사항

- **보안**: 비밀번호는 평문 저장 금지, 해시(bcrypt 등) 저장 — 상식 수준의 기본 보안만 적용하고 별도의 고급 인증체계(2FA, SSO 등)는 두지 않는다.
- **인증 방식**: 세션 기반 인증(httpOnly 쿠키 + 서버 세션)을 사용한다. 외부 파트너/서드파티에 API를 개방할 계획이 없고 네이티브 모바일 앱도 없으므로(모바일은 반응형 웹으로만 대응) JWT의 이점(무상태, 다중 클라이언트 간 토큰 공유)을 살릴 곳이 없다. 세션이 즉시 무효화(로그아웃/보안사고 대응)가 쉽고 1인·5일 일정에 맞는 검증된 라이브러리(express-session 등)로 충분하다.
- **반응형 UI**: 데스크톱 우선으로 설계하고 모바일은 별도 네이티브 앱 없이 반응형 레이아웃으로만 대응한다.
- **접근성**: 이번 MVP 범위에서 a11y는 고려하지 않는다.
- **알림 신뢰성**: 이메일 발송 실패가 영업일지/코멘트 저장에 영향을 주지 않는다 (RULE-NOTIFICATION-001) — 저장이 우선, 알림은 부가 기능으로 취급.
- **STT 가용성**: 브라우저 호환성과 인식 정확도를 보장하지 않으며, 실패 시 텍스트 입력으로 항상 대체 가능해야 한다 (RULE-STT-007).
- **성능/확장성**: 별도의 정량적 목표(동시접속자 수 등)는 두지 않는다. 1인 개발 MVP 규모에 맞는 단일 서버 구성으로 충분하다.

## 7. 기술 스택 및 아키텍처 개요

- **Frontend**: React (반응형 UI, 데스크톱 우선 + 모바일 대응).
- **Backend**: Node.js + Express, REST API 단일 서버.
- **인증/세션**: `express-session` + `connect-pg-simple`로 세션을 기존 PostgreSQL에 그대로 저장한다(Redis 등 별도 세션 저장소 인프라를 새로 두지 않는다). 프론트엔드와 백엔드를 다른 origin으로 배포할 경우 쿠키에 `SameSite=None; Secure`와 CORS `credentials: true` 설정, HTTPS가 필요하다 — 가장 단순한 구성은 Express가 React 빌드 결과물을 같은 origin에서 서빙하는 것이다.
- **Database**: PostgreSQL. 주요 엔티티: 사용자(users), 거래처 마스터(customers), 영업일지(sales_logs), 코멘트(comments) 정도로 단순 구성 — 마이크로서비스, 메시지 큐, 캐시 레이어 등은 두지 않는다(오버엔지니어링 금지, 1인/5일 규모에 불필요).
- **거래처 마스터**: 관리자 화면 없이 DB에 직접 INSERT하여 등록·관리한다 (RULE-CUSTOMER-003). 초기 데이터는 시드 스크립트나 수동 SQL로 입력.
- **STT**: 브라우저 내장 Web Speech API를 프론트엔드에서만 사용하고, 백엔드는 변환된 텍스트만 전달받는다 (RULE-STT-001). 별도 음성 처리 서버는 없다.
- **이메일 발송 (리스크)**: Nodemailer 등으로 실제 SMTP 발송을 시도하되, 실제 이메일 계정/서비스 연동 여부가 아직 정해지지 않았다. 개발 중에는 콘솔 로그로 발송 내용을 대체할 수 있으며, 이는 명확한 리스크로 남긴다 — 실사용 전 실제 SMTP 서비스(예: 무료 티어) 연동이 필요하다.
- **외부 연동**: Google Calendar, Slack 등은 이번 범위에 포함하지 않으며 추후 연동 예정으로만 남긴다.

## 8. 우선순위 (P0/P1)

### P0 — 핵심 플로우 (회원가입 → 영업일지 작성 → 코멘트 → 조회)

- 회원가입/로그인 (UC-001, UC-002)
- 조직·상사 관계 매핑 기본 (RULE-ORG-001~004, 007, 008)
- 거래처 마스터 시드 데이터 및 선택 UI (RULE-CUSTOMER-001~003)
- 영업일지 작성/수정/삭제 (RULE-LOG-001~005, UC-003, 005, 006)
- 팀장 영업일지 조회 (UC-007, RULE-ORG-008)
- 코멘트 스레드 — 팀장 피드백 + 영업사원 답변 (RULE-FEEDBACK-001~004, RULE-REPLY-001~005)
- 이메일 알림 최소 구현 (RULE-NOTIFICATION-001)
- 개인 영업일지 조회/검색 (RULE-SEARCH-001)
- 영업일지 상태 표시 (섹션 16)

**근거**: 이 9가지가 없으면 도메인 정의서 2번(핵심 업무 흐름) 자체가 완성되지 않는다 — 시스템의 존재 이유인 "기록→코칭" 순환이 성립하지 않는다. 팀장 영업일지 조회(UC-007)는 팀장이 코멘트를 남기려면 먼저 영업일지를 확인해야 하므로 핵심 업무 흐름 7~8단계의 필수 선행 기능이며, 어차피 코멘트 스레드를 구현하려면 함께 만들어야 하는 화면이라 별도의 개발일이 추가되지는 않는다.

### P1 — 나중에 잘라낼 수 있는 것

- STT 음성 입력 (RULE-STT-001~007, UC-004)
- 거래처 Know-how 공유 및 조직 범위 필터링 (RULE-KNOWHOW-001~006, UC-011)
- 미가입 팀장 자동 연결 로직 (RULE-ORG-005, UC-013)

**근거**: STT는 텍스트 입력이 항상 대체 가능한 보조 수단이라 도메인 정의서 스스로도 가용성을 보장하지 않는다고 명시한다(RULE-STT-007). Know-how 공유는 조직 범위 조인 쿼리가 필요해 개발 비용이 상대적으로 크고, 없어도 개인 영업일지 관리라는 핵심 흐름은 그대로 동작한다. 팀장 자동 연결은 데모/테스트 시 팀장을 먼저 가입시키면 우회 가능한 예외 케이스다.

## 9. 일정 (마일스톤)

1인 개발자 기준, 5일 촉박 일정을 감안한 현실적 계획이다. 인증 + 4개 엔티티(사용자/거래처/영업일지/코멘트) CRUD + 팀장 조회 + 코멘트 스레드 + 이메일 알림 + 검색까지가 P0 전체 범위이며, 냉정히 보면 5일은 절대 여유롭지 않다 — UI 스타일링은 최소 수준으로 제한하고 자동화 테스트 대신 수동 확인으로 대체하는 것을 전제로 해야 성립하는 일정이다. 이 전제가 무너지면 P1(STT, Know-how 공유, 팀장 자동 연결) 순서대로 먼저 잘라낸다.

- **Day 1**: 프로젝트 셋업(React + Express + PostgreSQL), DB 스키마 설계(users, customers, sales_logs, comments), 회원가입/로그인 API + 화면 (RULE-AUTH-001~006, RULE-USER-001~002, RULE-ORG-001~004)
- **Day 2**: 거래처 마스터 시드 데이터 입력, 영업일지 작성 API + 화면, 영업일지 목록 조회 (RULE-CUSTOMER-001~003, RULE-LOG-001)
- **Day 3**: 팀장 View(소속 영업사원 영업일지 목록/상세 조회, UC-007), 영업일지 수정/삭제(삭제 제한 규칙 포함), 코멘트 스레드(팀장 피드백 + 답변) API + 화면, 상태 표시 (RULE-ORG-008, RULE-LOG-002~005, RULE-FEEDBACK-001~004, RULE-REPLY-001~005)
- **Day 4**: 이메일 알림(Nodemailer, 실패해도 저장 유지), 개인 조회/검색 화면, 반응형 레이아웃 다듬기 (RULE-NOTIFICATION-001, RULE-SEARCH-001)
- **Day 5**: STT 음성 입력(P1), 거래처 Know-how 공유 화면(P1), 미가입 팀장 자동 연결 로직(P1), 통합 테스트 및 버그 픽스, 배포 (RULE-STT-001~007, RULE-KNOWHOW-001~006, RULE-ORG-005)

P1 항목(STT, Know-how 공유, 팀장 자동 연결)은 Day 5에 몰려 있어 일정이 밀리면 가장 먼저 잘려나갈 후보다.

## 10. 리스크 및 미해결 사항

**도메인 정의서 21.2 남은 결정 사항 (원문 번호 그대로 인용 — 21.1에서 1, 2, 3, 4, 6번이 해결되었고 5, 7번만 미해결로 남았다)**:

- **[21.2 항목 5]** 정성적 영업활동 여부를 판단하는 구체적인 검증 방식 → 아직 미확정, 추후 별도로 구체화 필요.
- **[21.2 항목 7]** 영업활동에 고객 개인정보가 포함되는 경우 공유 범위를 어떻게 통제할지 → 현재는 통제하지 않음(MVP 범위 제외), 실사용 전 재검토 필요.

**5일 일정 자체의 리스크**:

- 1인 개발 + 5일이라는 절대 시간 부족으로 P1 항목(STT, Know-how 공유, 팀장 자동 연결)이 일정 초과 시 통째로 누락될 가능성이 높다.
- 이메일 실제 발송 인프라(SMTP 계정 등)가 준비되지 않으면 개발 완료 시점까지 콘솔 로그 대체 상태로 남을 수 있다.
- 테스트 커버리지가 최소 수준에 그칠 수밖에 없어 회귀 버그 리스크가 존재한다.
